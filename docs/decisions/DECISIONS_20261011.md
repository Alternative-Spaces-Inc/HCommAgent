# HCA design decisions (2026-10-11)

7. P21a owner selections (15:2x PT, two widgets, one decision each, after PR 108 merged as main bcb1a18a): (1) webhook destinations are registered once by the caller (POST /v1/webhooks under the caller's api key, HMAC secret returned once, SSRF rules applied at registration and again at send on the pinned address), and an ask whose deliver_to.url is not a registered, non revoked destination of that caller and tenant is rejected with 400 (declined: auto-register on first use, allow unsigned raw urls beside registered ones for now); (2) the durable outbox on the scheduled_jobs table retries a failing destination 7 times over about one hour (1 s, 5 s, 30 s, 2 min, 10 min, 30 min, 1 h, each with up to 20 percent jitter) and then marks the delivery dead with an audit row (declined: about 24 hours in 10 attempts, keep today's 3 attempts made durable). Plan: docs/plans/HCA_P21A_WEBHOOK_SECURITY_v1.md.

8. P21a webhook secrets at rest (16:5x PT, one widget, after PR 109 merged as main 6b02cf5f): Day 1 stored the destination secret as a one way hash, which verifies a presented secret but cannot sign a delivery. The server keeps each destination secret encrypted with AES-256-GCM under a key derived by HKDF-SHA256 from the existing api key pepper (HCA_API_KEY_PEPPER, Secret Manager), the destination id as associated data (api/app/webhook_crypto.py). No new credential; a dumped table stays useless without the pepper; rotating the pepper makes stored secrets unreadable, so a pepper rotation must be followed by destination rotations (deliveries to such a destination fail dead with the reason recorded). Declined: a dedicated HCA_WEBHOOK_KEY secret minted in Secret Manager (separate blast radius, one more Console step), a plaintext column.
