# HCA design decisions (2026-10-15)

1. P23 owner selection 2, notification fallback surface (06:4x PT, one widget, after the P23 plan v1 merged as HCommAgent PR 25, main 9183729a): when a notification click cannot open the popup (`chrome.action.openPopup()` rejects: no focused window, another popup open), the extension opens a full tab decision page `decision.html?request=<id>` at phone width showing that one ask with the action bar pinned; a second click while that tab exists focuses it instead of opening another; closing a notification clears nothing, the ask stays in the inbox until answered or expired. Implementation note: the open tab is remembered by id in `chrome.storage.local` (`hca_decision_tab`) and checked with `chrome.tabs.get`, because `chrome.tabs.query` by URL would need the `tabs` permission and the manifest permission list is pinned by `tests/pack.test.js`. Declined: the options page with the ask focused (one page fewer, but the settings form shares the viewport); do nothing on refusal (the behaviour before P23, silent). Plan: docs/plans/HCA_P23_EXTENSION_HARDENING_v1.md sections 3 and 6. Selections 1 (device rotation model, Day 3) and 3 (browser suite placement, Day 2) remain open; Day 1 (p23/day1-client) starts.

2. P23 owner selection 3, browser suite placement (07:1x PT, one widget, while PR 26 checks ran): all nine browser proof scenarios (the eight program scenarios in plan section 4 plus the layout proof `extension/tests/layout.proof.mjs`) run in the existing extension CI job on every pull request, six minute budget, so a layout, click path or offline queue regression fails the PR before merge. Declined: a nightly scheduled job for the nine with pull requests keeping only the two existing scenarios (faster PRs, a regression could merge and be caught the next morning). Plan: docs/plans/HCA_P23_EXTENSION_HARDENING_v1.md section 4. Selection 1 (device rotation model, Day 3) remains open; Day 2 (p23/day2-proofs) starts after PR 26 merges.
